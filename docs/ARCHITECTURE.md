# المعمارية

## نظرة عامة

```
 متصفح العميل ─► المتجر (ملفات ثابتة) ──┐
 المدير ───────► لوحة الإدارة ──────────┤  HTTPS
                                        ▼
                         API  (Cloudflare Worker: fetch(Request)→Response)
                                        │  PostgREST / RPC
                                        ▼
                         Supabase Postgres  ← كل منطق الأعمال دوال SQL
                                        ▲                      ▲
             /sync/push · pull · snapshot│                      │ pg_dump + /sync/weekly-export
                        ┌───────────────┴──┐            ┌──────┴────────┐
                        │ Branch Agent     │            │ Server Agent  │
                        │ SQLite + outbox  │            │ نسخ/تصدير/مراقبة│
                        │ كاشير بدون نت    │            └───────────────┘
                        └──────────────────┘
```

**مبدأ التصميم:** الفرع لا يتوقف أبدًا بسبب الإنترنت. كل ما يلمسه الكاشير (بحث، بيع، مرتجع، جرد، استلام، حضور) يُنفَّذ على SQLite محلي ثم يُرسَل لاحقًا. السحابة هي المرجع النهائي وتُعيد توزيع التغييرات.

## الطبقات

1. **قاعدة البيانات (`db/`)** — الحقيقة الوحيدة. الجداول مقفولة (`099_security.sql`) لـ `service_role` فقط. المعاملات والحجز الذري والمزامنة كلها داخل دوال SQL (`apply_ops`, `pull_changes`, `create_online_order`, `transition_transfer`…)، فلا تتأثر بسباق الطلبات ولا بنوع الاستضافة.
2. **الـ API (`2-api/`)** — معالج `fetch` واحد، يعمل كما هو على Workers وNode. يتحقق من الصلاحية والمدخلات ثم يستدعي دالة SQL. سائق قاعدة البيانات قابل للتبديل: `psql` (اختبارات)، `pg`، أو PostgREST (Supabase).
3. **الحزمة المشتركة** — منطق يجب أن يتطابق بين الطرفين: توليد/فك الأكواد، حساب الفاتورة بالقروش، قواعد الحضور، الصلاحيات، `customerIdFor`، عقد المزامنة، مولّد الفاتورة.
4. **التطبيقات** — واجهات عربية RTL بـ ES modules عادية.

## المزامنة

### الرفع (الفرع ← السحابة)
- كل عملية في جدول `outbox` بمعرّف `opId` (UUID) ثابت ونوع: `sale.create`, `customer.upsert`, `attendance.record`, `stock.count`, `transfer.receive`, `shift.close`.
- `POST /sync/push` بدفعات ≤ 100. السيرفر يسجّل `processed_ops` أولًا: المعرّف المكرر يُردّ `duplicate` فلا تتكرر فاتورة أبدًا (إعادة الرفع آمنة).
- فشل عملية لا يوقف باقي الدفعة (`status:'error'` مع السبب)، وتظهر للمدير في «الإعدادات ← المزامنة» مع زر إعادة المحاولة.
- الشبكة تنقطع ⇒ تبقى `pending` وتُعاد بتأخير تصاعدي (حتى 5 دقائق)؛ وتُدفع فورًا بعد كل عملية (debounce 1.5 ث).

### التنزيل (السحابة ← الفرع)
- `change_log` يُملأ بـ triggers على كل جدول مشترك. الفرع يحفظ آخر `seq` ويسحب `GET /sync/pull?after=` على صفحات ≤ 500.
- الجهاز الجديد أو المتأخر بعد قصّ السجل (30 يومًا) يحصل على **لقطة كاملة** (`/sync/snapshot`) ثم يكمل بالمؤشر.
- التغييرات الخاصة بفرع (حركات المخزون) تُرسَل لذلك الفرع فقط. أسعار التكلفة تُحذف من اللقطة ومن سجل التغييرات (trigger) ولا تصل للفرع، وهذا مغطّى باختبار.

## المخزون

- **دفتر حركات** `stock_movements` (لا يُعدَّل، فقط يُضاف) + `stock_balances` كرصيد مُخزَّن يُحدَّث بـ trigger.
- نفس `id` للحركة في الفرع والسيرفر ⇒ عند عودة الحركة في التنزيل تُهمَل (`INSERT OR IGNORE`) فلا يُحتسب الرصيد مرتين. هذا مغطّى باختبار صريح.
- **البيع بدون رصيد كافٍ** لا يُرفض في السيرفر: تُسجَّل الفاتورة وتُعلَّم `oversold` للمراجعة (القطعة معه فعلًا، والمنع يضيّع بيعًا حقيقيًا). الكاشير يرى تحذيرًا.
- **التحويلات:** مسودة ← معتمد ← في الطريق (يُخصم من المصدر وقتها) ← مستلم/مستلم جزئيًا. العجز يُسجَّل ولا يُخفى.

## المتجر الإلكتروني

- وضع مخزون الموقع (إعداد بمستوى «تصريح»): 1) المخزن الرئيسي فقط، 2) الرئيسي + فروع محددة، 3) كل الفروع، 4) مخزون منفصل `web_stock`.
- الطلب يحجز الكمية **ذريًا** داخل دالة واحدة (`create_online_order`) مع هامش أمان وحد «آخر قطع». الطلب المعلّق ينتهي حجزه بمهلة (Cron كل 30 دقيقة).
- حماية: honeypot + حد معدّل + `clientToken` لمنع تكرار الطلب عند إعادة الإرسال.
- التتبع: رقم الطلب + آخر 4 أرقام من الهاتف فقط.

## الصلاحيات والتصاريح

- أدوار: `super_admin`, `admin`, `branch_manager`, `storekeeper`, `accountant`, `cashier` (`permissions.js`). الأدمن لا يغيّر مستويات الإعدادات ولا يوافق على تصاريح نفسه.
- **مستويات الإعدادات:** `free` (يعدّلها الأدمن)، `grant` (يحتاج تصريحًا لمرة واحدة ومحدودًا بوقت من السوبر أدمن)، `super` (للسوبر أدمن وحده). السوبر أدمن يغيّر المستوى نفسه.
- كل تعديل إعداد له نسخة وتاريخ ويمكن استرجاعه (بتصريح)، وكل شيء حساس في `audit_log`.
- خصم الكاشير محدود بنسبة (`discount.cashier_max_pct`)، وما فوقها يحتاج مديرًا. الكاشير يرى الاسم وآخر 4 أرقام فقط من هاتف العميل.

## الأمان

| الموضوع | التنفيذ |
|---|---|
| كلمات السر | PBKDF2-SHA256 بـ 100,000 تكرار (حد Cloudflare)، ملح لكل مستخدم |
| جلسات الإدارة | JWT HS256 قصير العمر؛ قفل 15 دقيقة بعد 5 محاولات فاشلة |
| الأجهزة | توكن `id.secret` يظهر مرة واحدة ويُخزَّن مجزّأً SHA-256؛ يمكن إيقافه فورًا؛ إيقاف فرع كامل بإعداد kill-switch |
| دخول الكاشير بدون نت | يتحقق محليًا من verifier مُنزَّل (PBKDF2) مع قفل بعد 5 محاولات |
| الخادم المحلي للفرع | `127.0.0.1` فقط، فحص `Host` و`Origin`، توكن جلسة بعد الدخول |
| قاعدة البيانات | قفل الجداول لـ service_role: لا وصول مباشر من المتصفح، فقط عبر الـ API |
| الصور | تُرفع لـ R2 (WebP/JPG/PNG فقط بفحص محتوى الملف، حتى 1.5MB) |

## الطباعة

الفاتورة والملصق يُرسمان على Canvas بخط حقيقي (لتجنب مشاكل العربية في أكواد الطابعات)، ثم يُحوَّلان لنقاط 1 بت ويُرسلان: **ESC/POS** (`GS v 0`) للفواتير و**TSPL** (`BITMAP`) للملصقات. الناقلات: شبكة (9100)، ملف/جهاز، طابعة ويندوز مشتركة، ومعاينة. باركود Code128 و QR مولّدان في الكود نفسه. **لم يُختبر على طابعة فعلية** — جرّب أول طباعة قبل التشغيل الفعلي (ARCHITECTURE تذكير: في TSPL البت 0 = أسود، وقد يختلف موديل لآخر؛ لو خرجت الصورة معكوسة بدّل المنطق في `tsplBitmap`).

## حدود معروفة

- مرتجع الفاتورة يلزم أن تكون الفاتورة الأصلية مسجّلة على نفس جهاز الفرع (الفواتير الأقدم من تثبيت الجهاز غير موجودة محليًا).
- جهاز كاشير واحد لكل فرع هو الحالة المختبرة؛ لأكثر من جهاز اضبط `posNo` ليختلف ترقيم الفواتير.
- لوحة الإدارة تحتاج إنترنت (لا offline للإدارة).
